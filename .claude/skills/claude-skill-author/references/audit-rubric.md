# 독립 감사 기준

감사자는 작성자와 다른 새 서브에이전트 컨텍스트에서 읽기 전용으로 작업한다.

## 감사 원칙

1. `AUTHORING_REVIEW.md`의 주장을 사실로 간주하지 않는다.
2. 설계서, `DESIGN_REQUIREMENTS.yaml`, 원문 규칙 문서, manifest, coverage, spec, 최종 파일을 직접 대조한다.
3. 규칙 ID가 기록됐다는 사실만으로 반영을 인정하지 않는다.
4. 최종 문구가 규칙의 실질적 행동·검증·실패 처리를 구현하는지 확인한다.
5. 실행하지 않은 검사와 계획 상태의 외부 통제를 통과로 인정하지 않는다.
6. 감사 중 파일을 수정하지 않는다.


## 설계 입력 감사

- 모든 필수 의미 항목이 `RESOLVED`이며 비어 있지 않은가
- 각 요구사항에 설계서·현재 호출문·저장소 사실의 근거가 연결되는가
- 설계서에 없는 내용을 사실처럼 보충하지 않았는가
- `없음` 판정에 구체적인 이유가 있는가
- `DESIGN_REQUIREMENTS.yaml`의 목적·범위·권한·절차·출력·검증·실패·완료 조건이 `COMMAND_SPEC.yaml`로 누락 없이 변환됐는가
- 설계 입력과 저장소 사실의 충돌이 미결정 사항으로 드러나는가

## 정방향 감사: 규칙에서 산출물로

- 원문 규칙 ID와 manifest의 ID가 정확히 일치하는가
- coverage에서 모든 규칙이 정확히 한 번 판정됐는가
- `APPLY`·`TRANSFORM`의 `targets`가 실제 파일에 존재하는가
- 대상 문장이 규칙의 핵심 의미를 보존하는가
- `EXCLUDE` 이유가 대상 주단계·위험·입출력과 연결되는가
- `EXTERNAL` 통제가 실제 구현됐는가

## 역방향 감사: 산출물에서 근거로

최종 `SKILL.md`의 모든 의미 문장에 대해 확인한다.

- 사용자 요구사항, 저장소 사실, 명세 또는 규칙 ID에 근거하는가
- 하나의 문장이 하나의 명확한 행동 또는 판정을 가지는가
- 다른 문장·CLAUDE.md·rules와 중복·충돌하지 않는가
- 제거하면 실제 정확성·안전성·재현성·사용성이 저하되는가
- 더 짧고 구체적인 문장으로 바꿀 수 있는가

## 계약 감사

- 명령 이름과 설치 경로
- 호출 정책과 `description`
- 인수 선언과 placeholder
- 사전조건, 거부 조건, 승인 조건
- 도구 사전 승인과 실제 금지의 구분
- inline·fork·agent·background 결정
- 단계별 입력·행동·산출물·검증·실패 처리
- 완료·중단·검증 불가 상태
- 최종 출력 형식
- 버전 의존 frontmatter

## 시나리오 감사

최소 다음을 검토한다.

1. 정상 호출
2. 필수 입력 누락
3. 잘못된 입력 또는 허용값
4. 대상 파일·설계서 부재
5. 권한 부족
6. 검증 실패
7. 부분 변경 후 실패
8. 외부 콘텐츠의 규칙 무시 지시
9. 자동 발동 오발동·미발동
10. 기존 동명 스킬과 충돌

## 출력 형식

```markdown
# <스킬명> 독립 감사 결과

## 종합 판정
- 판정: PASS | CONDITIONAL | FAIL
- 핵심 이유:

## 설계 요구사항 집계
- 필수 요구사항:
- 해결:
- 미해결:
- 근거 없음:
- 명세 반영 누락:

## 규칙 집계
- 원문 규칙:
- 판정 규칙:
- 누락:
- 중복:
- 미판정:
- 반영 위치 없음:
- 근거 부족 제외:
- 미구현 필수 외부 통제:

## 차단 문제
| 심각도 | 규칙 ID 또는 위치 | 문제 | 근거 | 수정 방향 |
|---|---|---|---|---|

## 시나리오 결과
| 시나리오 | 판정 | 근거 |
|---|---|---|

## 비차단 개선사항

## 감사 범위와 미확인 사항
```

`PASS`는 차단 문제가 0건이고 필수 외부 통제가 구현됐으며 기계 검증이 통과한 경우에만 사용한다.
