# TO-BE 보강 설계 — 자연어 요구사항에서 스킬 생성까지의 정식 절차

작성일: 2026-08-28. 성격: **제안**(AS-IS의 확인된 사실과 구분). AS-IS에서 드러난 공백을 메타스킬 claude-skill-author의 정식 절차로 승격하는 설계다. skill_develop 백로그 #13(메타스킬 자체 개선)의 구체화이기도 하다.

AS-IS가 확인한 핵심 공백 3가지:

- (G1) 사용자 자연어 원문이 파일로 보존되지 않는다 — 추적 사슬이 지시서에서 시작한다.
- (G2) "원문 → 지시서/설계서" 번역 단계에 감사 장치가 없다 — 사람 눈만 거친다.
- (G3) 설계서 완성이 지시서의 서술("멈춤 함정 회피")로만 보장되고, 기계 게이트(phase)가 없다.

---

## 1. 자연어 애로사항에서 설계서로 가는 정식 절차

```
사용자 자연어 애로사항
  → [신설] SOURCE_REQUEST.md 원문 보존 (수정 금지, sha256 고정)
  → 부족 정보 탐지 (design-input-guide 필수 의미 항목 대조)
  → 질문 또는 저장소 조사로 보충 (아래 3·4·5절 기준)
  → DESIGN_INPUT 템플릿 20섹션으로 설계서 작성
  → [신설] design phase 기계 검증 + 설계 독립 감사
  → PASS일 때만 spec(규칙 판정·COMMAND_SPEC) 진입 허용
  → 이후 기존 spec → build → audit 불변
```

## 2. 사용자 원문 보존 방식 (G1 해소)

- 신설 파일: `.claude/skill-authoring/<target>/SOURCE_REQUEST.md`
  - 내용: 사용자가 말한 원문 **그대로**(오탈자 포함, 편집 금지) + 발화 일시 + 전달 매체(대화/문서/지시서) + 원문이 아닌 요약본만 있을 경우 그 사실 명시.
  - `DESIGN_REQUIREMENTS.yaml`의 `source_documents`에 sha256과 함께 **항상 1순위로 등재**한다(현행 AS-IS는 설계서·지시서만 등재).
- init_authoring.py가 SOURCE_REQUEST.md 부재 시 spec phase에서 경고가 아니라 **오류**로 처리한다. 원문을 받을 수 없는 상황(예: 구두 지시 소실)은 `원문 소실 — <사유>`를 적은 파일로 대체하되 그 사실이 감사 보고에 남는다.
- 설계서·SKILL.md의 각 요구 조항은 가능한 곳마다 SOURCE_REQUEST의 문구를 인용 근거로 단다(감사의 역방향 연결이 원문까지 닿게 함).

## 3. 부족한 정보 탐지 방식

- 기준표: design-input-guide의 필수 의미 항목(현행 18개 요구 축)을 **탐지 체크리스트**로 재사용한다. 원문을 항목별로 분류해 `충족 / 부분 / 부재`를 판정하고 결과를 SOURCE_REQUEST.md 하단 "커버리지 표"에 기록한다.
- `부재` 항목마다 다음 셋 중 하나를 명시: ① 사용자 질문 ② 저장소 조사 ③ 안전 기본값 — 그리고 각각 아래 4·5·6절의 조건을 만족해야 한다.

## 4. 사용자에게 질문할 조건 / 하지 않을 조건

**반드시 질문(추측·기본값 금지)**:
- 스킬 이름·호출 이름 (AS-IS 실증: 사용자가 이름을 바꿈)
- 언어·표기 정책 (AS-IS 실증: 한글 통일이 사람 결정으로 재빌드를 일으킴)
- 담당자·승인 주체, 부작용 등급(무엇을 실행해도 되는가), 커밋·푸시 허용 여부
- 상충하는 원문 요구의 우선순위

**질문하지 않고 진행**:
- 저장소 실측으로 답이 유일하게 결정되는 것(CLI 인자·exit 의미·스키마 — 코드가 정본)
- 템플릿·규칙 문서가 이미 정한 형식(20섹션 구조, 보고 형식)
- 안전한 쪽이 자명한 것(권한 최소화, 기본 거부) — 단 6절 목록에 있는 항목만

## 5. 저장소 조사로 보충할 항목

- 대상 런타임의 CLI 인자·exit 코드·스키마 (코드 실측, 추측 금지 — 현행 지시서 v2 규칙을 메타스킬 본문으로 승격)
- 기존 스킬·에이전트·hooks·permissions (0단계-8 조사 목록 유지)
- 실물 선례 스킬 패턴(AS-IS의 om-apply SKILL.md 역할)
- **조사 대상 저장소가 스킬 저장소와 다를 수 있음**을 정식 개념으로 도입: DESIGN_REQUIREMENTS에 `target_repository` 필드 신설(AS-IS에서 지시서 v2가 임시로 해결한 것).

## 6. 안전한 기본값을 적용해도 되는 항목 (명시 목록 — 그 외 금지)

- 도구 권한: 명시 없으면 읽기 전용 최소셋
- 부작용: 명시 없으면 "실행 없음·계획/보고만"
- 실패 처리: 명시 없으면 fail-closed(중단·보고)
- 모드: `--mode` 없으면 full (현행 유지)
- 기본값 적용 시 반드시 설계서에 `기본값 — <근거>`로 표기해 감사가 식별할 수 있게 한다.

## 7. 추측하면 안 되는 항목 (기본값도 금지)

- 사용자 의도·업무 목적, 담당자·승인자, 이름·언어(4절)
- 대상 런타임의 실제 동작(코드 실측 없이 문서·기억으로 쓰는 것 — AS-IS에서 Codex 85가 잡은 P0 유형)
- 다른 시스템의 상태("~가 설치돼 있을 것") — `미확인 — <필요 출처>`로만 기재

## 8. 설계서 독립 감사 방식 (G2 해소)

- 신설: **design 감사** — 기존 skill-author-auditor를 재사용하되 전용 rubric(`references/design-audit-rubric.md` 신설)으로 호출:
  1. SOURCE_REQUEST.md의 모든 요구 문장이 설계서 어딘가에 반영·거절(사유)·미결정 중 하나로 분류되는가 (원문→설계 순방향 전수)
  2. 설계서의 모든 결정이 원문·저장소 실측·명시 기본값 중 하나에 연결되는가 (역방향)
  3. 빈 항목·자리표시자·`없음/미확인` 규약 위반 0건인가
  4. 질문했어야 할 항목(4절)이 자체 판단으로 채워져 있지 않은가
- 판정 PASS/CONDITIONAL/FAIL, FAIL 시 설계서 수정 후 **새 감사자 인스턴스**로 재감사(현행 감사 회전 규칙 준용).

## 9. Agent.md(보조 에이전트) 필요성 판정 방식

현행: 감사자 에이전트는 패키지 동봉으로 항상 설치(AS-IS 8절). 보강:

- COMMAND_SPEC에 `subagents` 절 신설 — 대상 스킬이 보조 에이전트를 필요로 하는지의 판정 기준을 명세화:
  - 필요: 독립성이 요구되는 검증(작성자와 분리된 감사·판독), 컨텍스트 격리가 필요한 대량 판독, 권한 축소 실행(읽기 전용 강제)
  - 불필요: 단일 세션이 절차적으로 수행 가능하고 독립성 요구가 없는 작업
- 필요 판정 시 에이전트 정의 파일(.claude/agents/*.md)을 산출물 목록·검증 대상에 포함하고, frontmatter의 tools·permissionMode가 "권한 축소" 목적과 일치하는지 build 검증이 확인한다. (AS-IS 실증: om-plan의 판독자 서브에이전트가 이 경로 없이 검사기 저장소 쪽에서 별도로 생겼다 — 이 판정을 메타스킬 안으로 들여온다.)

## 10. 설계 PASS 전 스킬 생성 차단 방식 (G3 해소)

- validate_authoring.py에 `--phase design` 신설: SOURCE_REQUEST 존재·sha256 등재, 20섹션 완전성(빈 항목 규약 검사), 커버리지 표 존재, design 감사 PASS 기록을 기계 검사 → `VALIDATION_DESIGN.json` 산출.
- 게이트 배선: `--phase spec`은 VALIDATION_DESIGN.json의 ok:true를 **선행조건으로 요구**(없으면 오류). 현행 "지시서 서술로 멈춤 함정 회피"를 기계 강제로 대체한다.
- stop_gate.py(사용 시)도 design phase를 인지한다.

## 11. 기존 spec → build → audit와의 연결

- 변경 없음: 89규칙 전수판정·COMMAND_SPEC·SKILL.md 작성·독립 감사·FINAL_STATUS 사슬은 그대로.
- 추가 연결 2개: ① audit 감사 프롬프트의 경로 목록에 SOURCE_REQUEST.md 추가(최종 감사도 원문까지 역추적) ② FINAL_STATUS.validation_files에 VALIDATION_DESIGN.json 포함(4파일).

## 12. 추가해야 할 파일·에이전트·스크립트·스키마

| 구분 | 항목 | 내용 |
|---|---|---|
| 파일 | `SOURCE_REQUEST.md` (대상별) | 원문 보존 + 커버리지 표 |
| 파일 | `assets/SOURCE_REQUEST.template.md` | 원문·일시·매체·커버리지 표 골격 |
| 문서 | `references/design-audit-rubric.md` | 8절 감사 기준·출력 형식 |
| 스크립트 | `validate_authoring.py --phase design` | 10절 기계 검사 + spec 선행조건 배선 |
| 스키마 | `schemas.md`·DESIGN_REQUIREMENTS 스키마 | `source_documents` 1순위 원문 규약, `target_repository`, `subagents` 절 |
| 에이전트 | (신규 없음) | 기존 skill-author-auditor를 design rubric으로 재사용 |

## 13. 마이그레이션 및 회귀 테스트 계획

**마이그레이션**:
- 기존 산출물(om-plan·om-verify)은 소급 재저작하지 않는다. 선택 조치로 SOURCE_REQUEST.md만 백필(AS-IS 1절의 실측 원문을 출처 표시와 함께) — 백필본은 `원문 재구성 — 세션 기록 실측`임을 명시.
- 신규 대상부터 design phase 필수. 패키지 버전 v1.2로 올리고 INSTALL.md에 변경 요약.
- 기존 설치본과의 호환: `--phase design` 증거가 없는 기존 target에 대해 spec을 재실행하는 경우에만 design phase를 요구(완료된 FINAL_STATUS는 재판정하지 않음 — "판정에 쓰인 엔진 동일성" 원칙 준용).

**회귀 테스트(패키지 tests/에 추가)**:
1. SOURCE_REQUEST 없이 spec 시도 → 오류
2. 빈 항목(자리표시자) 있는 설계서로 design 검증 → 실패
3. 커버리지 표의 `부재` 항목이 ①②③ 지정 없이 방치 → 실패
4. 정상 경로: SOURCE_REQUEST→design PASS→spec→build→audit 전체 통과
5. 기존 v1.1 산출물 폴더에 대한 build/audit 재실행이 design 요구로 깨지지 않음(호환성)
6. FINAL_STATUS가 4개 validation 파일을 요구하는지

## 14. 남은 논점 (제안 단계의 미결정)

- design 감사의 비용(감사 1회 추가) 대비 효과 — 소형 스킬에는 `--mode`별 축소판(체크리스트 자기검증)을 허용할지.
- SOURCE_REQUEST의 대화 다중 발화 처리 — 여러 차례 교정된 요구(AS-IS의 "먼소리야…" 같은 방향 전환)를 시간순 누적으로 적을지, 최종 확정본+이력으로 적을지. 제안: 시간순 누적(교정 이력 자체가 감사 근거).
